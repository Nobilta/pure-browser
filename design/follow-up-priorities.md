# 0.5.2 系统审查与优化优先级

2026-09-10，审查基线为 `7045e7862a00adc54e47ae80615e0bef15a15de4`。
本文件是当前项目的改进清单。建议项尚未实现；当前功能、安装包及发布测试仍以
[README](../README.md) 和 [模拟器报告](../EMULATOR_TEST_REPORT.md) 为准。

本轮检查了源码结构，重点阅读导航、标签、请求拦截、Rust 过滤、数据存储、下载、网站设置、
隐私、脚本和主要 Compose 页面；复核了 0.5.2 的菜单、工具栏及大字体截图。
另用当前 Rust 引擎运行 6 个独立域名检查，并按当前表结构检查主机 SQLite 查询计划。
这次没有重新运行 APK 的完整功能矩阵，也没有新增真机帧率、功耗或页面性能测量。

**近期收益主要来自正确性、状态管理和常用操作效率。** 当前已有完整浏览、菜单逐级返回、
站点设置及权限、书签 HTML 导入导出、最近关闭、阅读与纯文字离线保存、打印/PDF、分段续传、
过滤订阅、有限 GM API、全屏控件与 DLNA 控制。后续应以这些功能的完成质量为基础安排改造。

P1 表示应进入近期工作，P2 表示核心问题稳定后安排，P3 表示需要独立产品决策。
“已复现”是本轮运行得到的结果；“源码确认”描述现有实现；“待验证”表示影响尚需设备场景确认。
成本中的“小”为局部改动，“中”为跨模块及回归，“大”为状态/数据迁移或外部服务工程。

**Rust 应继续承担有明确输入输出的计算核心。** 使用 Rust 的理由应包括正确性复用、可测的
CPU/内存收益或跨平台需求；不能仅按 Kotlin 文件长度决定迁移。

| 范围 | 建议 | 收益与成本 | 优先级 |
|---|---|---|---|
| 网络过滤的站点身份、规则语义 | 在现有 Rust 过滤核心引入正确的可注册域判断，完善兼容测试 | 直接改善误拦/漏拦；需维护 Public Suffix List 数据及更新策略，成本中 | P1 |
| 过滤请求热路径与列表加载 | 先测 JNI 字符串复制、域名重复解析、匹配和引擎切换；按热点优化 | 可预计算当前文档上下文、减少分配；冷启动确有瓶颈时再做带版本/内容哈希的预编译规则快照，成本中 | P2，测量先行 |
| 用户脚本匹配、过滤订阅文本校验 | 先在 Kotlin 预解析模式、复用 URL 结果；大量脚本/列表形成热点后再评估批量 Rust 接口 | 当前规模有界，逐条 JNI 调用可能抵消收益，成本小至中 | P2，条件项 |
| HLS/DASH 清单解析、批量媒体元数据 | 若增加清晰度/音轨选择或离线媒体处理，可将纯解析放进 Rust | 当前主要是有限候选 URL 和播放器事件，尚不足以支持迁移决定，成本中至大 | P2，随功能立项 |
| 备份归档、跨平台同步的数据处理 | 功能规模或跨平台需求形成后，评估成熟 Rust 库的压缩/格式处理 | 密钥保护仍交给 Android Keystore；小型本地备份可先用 Android/JVM 能力，成本中至大 | P2/P3 |
| Compose UI、WebView 导航、权限、生命周期 | 保持 Kotlin，按状态所有者整理 | JNI 不能改善 Android 生命周期语义；迁移会扩大调试边界 | 持续维护 |
| SQLite、HTTP 下载、SAF/MediaStore、通知、DLNA | 保持 Kotlin 与系统组件，优化查询、调度、协议兼容 | 主要成本在 I/O、状态与设备适配，另引数据库/HTTP/TLS 栈缺少收益依据 | 持续维护 |
| DOM 探针、文章提取、用户脚本执行 | 保持 JavaScript，优化注入和 DOM 算法 | Rust 无法直接替代页面 DOM；复制整页跨语言处理会增加开销 | 持续维护 |

现有 Rust release 使用 `opt-level = "z"`，偏向体积。可以对过滤 crate 做 `z` 与 `2/3` 的
受控比较，记录匹配 P95、加载耗时、峰值内存和最终 APK 大小，再决定配置。
WebView 渲染和网页 JavaScript 执行由 Chromium 负责，改写应用外壳不会使这部分自动变快。
网络请求拦截需要同步回答，不能为了减少 JNI 次数无限攒批；适合批处理的是规则加载和离线解析。

**过滤器存在本轮已复现的语义问题，应先修正确性。**
[Matcher.should_block](../rust/adblock/src/matcher.rs) 用“两个主机是否互为后缀”判断第三方。
例如 `www.example.com` 请求 `cdn.example.com/app.js`，两者属于同一可注册域，当前却被当成第三方。
启用 `$third-party` 或 `$~third-party` 条件的规则因此可能出现误拦或漏拦；并非所有同站请求都会被拦截。

| 当前引擎的独立检查 | 实际是否拦截 | 预期是否拦截 | 结果 |
|---|---|---|---|
| `www.example.com` → `cdn.example.com`，规则 `cdn` 主机的 `$third-party` 条件 | 是 | 否 | 不符合 |
| 同一请求，规则改为 `$~third-party` 条件 | 否 | 是 | 不符合 |
| `www.example.com` → `cdn.other.com`，匹配 `$third-party` 规则 | 是 | 是 | 符合 |
| `example.com` → `cdn.example.com`，匹配 `$third-party` 规则 | 否 | 否 | 符合 |
| `www.example.co.uk` → `cdn.example.co.uk`，匹配 `$third-party` 规则 | 是 | 否 | 不符合 |
| `alice.github.io` → `bob.github.io`，匹配 `$third-party` 规则 | 是 | 是 | 符合 |

第一条实际规则为 `||cdn.example.com^$third-party`，第二条为 `||cdn.example.com^$~third-party`；
其余规则采用对应请求主机，类型均为 Script。修正时不能简单取最后两段域名：`co.uk`、
公共托管平台的独立租户、IP、localhost、IDN 都需覆盖。
过滤的同站身份、桌面显示入口分组和权限 origin 是三种用途；权限继续按协议、主机和端口隔离。
0.5.2 的桌面别名前缀策略已解决 JRS 循环；后续应补公共后缀边界测试，避免把特殊注册域的
`m.`、`www.` 当作普通展示别名。证据为本地
`validation/results/release-0.5.2/system-review/rust-domain-probe.json`，不是新增的通过发布测试。

**标签体验的主要取舍是内存与页面连续性。** 当前 `TabState` 保存 Bundle、URL、标题和缩略图，
[loadCurrentTab](../app/src/main/java/com/mybrowser/MainActivity.kt) 必要时销毁当前 WebView，
用新的实例 `restoreState`。这可以控制内存并恢复导航，但不等于保留 DOM、JavaScript 内存、
未提交表单、滚动及播放器状态。WebView 池的容量也不等于驻留同样数量的网页标签。

建议先做表单、长文章、SPA、视频四类切换夹具，再评估保留最近 1–2 个普通标签的活 WebView。
低内存设备降低预算；离开标签时明确媒体暂停和后台行为，无痕实例独立管理。
其余标签继续轻量保存，并明确“已休眠/重新加载”状态。成本大，P2；不要承诺任意页面都能完整恢复。

Cookie 存储不能视为密码库；未见显式 Autofill 配置也不能推导出系统自动填充一定不可用。
网页 Service Worker、WebSocket、跨域 iframe 和部分请求信息受 WebView API 限制，需要真实夹具确认过滤边界。
另写 Rust HTTP 客户端不会自动接管 Chromium 网络栈；自建 DNS/代理、完整扩展或独立渲染解码引擎都应单独评估。

**架构调整应围绕状态所有者进行。** 当前 MainActivity 约 2,500 行，同时管理平台回执、
导航/标签、弹层、网站权限、导入导出和媒体。存储及部分状态机已经下沉，下一步可逐项分离：

- 导航会话持有当前文档身份、WebView 所有权和恢复策略；把已有 URL、页面代次和回调有效性规则统一。
- 菜单继续由 BrowserSheetNavigation 管理；媒体全屏、文件选择、站点权限分别持有自己的进行中操作。
- Compose 只读取适合界面的状态并发送动作；订阅与前后台生命周期一致，持久任务留在进程级仓库。
- 降低 TabState 可变字段与手动 revision 通知的耦合，在实际漏通知/测试成本出现的边界使用不可变快照。
- 批量元数据写入采用明确的串行队列和失败结果；不要为拆文件引入层层互相回调。

这些属于 Kotlin 重构。需要保留现有页面代次、旧回调丢弃、单事务导入及下载每任务锁等正确性约束。
