## 维护规则

1. **一个主题一个维护位置。** 设计规范说明应该怎样，架构说明现在怎样实现，测试指南说明怎样验证。实际验证结果保留在生成报告中；其他文档只作摘要和链接。
2. **保留产品契约。** 无痕隔离、已接受下载、后台标签无数量上限等既定行为不能因重构或测试失败自行改写。发现实现与契约不一致，先核实错误路径；不得修改旧测试来掩盖回归。
3. **禁止过度防御性编程。** 修复可复现问题或明确外部边界；不为假设风险增加吞错、重复校验、重试层、默认成功、状态镜像或备用实现。性能改动先测量。规范例外写在对应规则旁，避免批量机械替换。
4. **README 保持中英同步。** 两份 README 保留相同章节与链接，介绍核心能力和快速开始；详细规则放在这里。其他正文默认中文，技术标识保持原文，不要求维护整套重复译本。
5. **链接可移植。** 仓库内使用相对路径；代码定位写文件及函数/类型，不以易失效的行号作为唯一定位。命令从仓库根目录运行，使用示例变量，不写维护者个人目录。
6. **避免实现副本。** 组件签名、完整函数、工具版本和阶段列表优先链接源码或配置；确需速查的 Token 表与命令在实现变化时同步。不建立文档专用版本配置或生成框架。
7. **仅保留当前维护内容。** 已完成待办、会话总结、重复审查报告和旧方案从正文移除；不另建副本或历史目录。changelog 只在正式发布成功后追加对应版本，不写测试包、未发布改动或发布计划；发布前的说明在 Git 外准备。第三方许可证保留其来源与历史事实。
8. **验证可追溯。** 测试方法写在 testing；实际报告、日志、截图、APK 与生成附件留在 Git 外，交付回复说明本次结果、失败与未覆盖范围。不另写人工验证记录，不把某次测试数字或“已全部通过”复制到长期文档。
9. **按影响验证。** 纯文档改动检查链接、命令及源码一致性；修改发布或验证脚本，运行对应检查。没有应用代码变化时，无需为整理文字重建 APK 或重跑整套设备回归。

## 改动时同步什么

| 变化 | 更新位置 |
|---|---|
| UI 约束或组件契约 | design-system；用户行为改变时再更新 features |
| 无痕数据归属或退出边界 | incognito-policy、对应测试；需用户明确设计变更 |
| 依赖、构建、模拟器 | building；入口命令改变时同步中英 README |
| 状态所有者、模块职责 | architecture |
| 测试入口或验收要求 | testing；实际执行结果保留在生成报告中 |
| 发布脚本或流程 | releasing；正式发布成功后将该版说明写入 changelog |
| 用户功能、限制 | features；核心能力改变时同步中英 README |

文档正文集中在本目录。根目录保留 README、AGENTS、LICENSE 与社区入口；模板留在 `.github/`，图标源文件留在 `design/`，APK 内声明和许可证留在资源目录。迁移路径时同时更新调用脚本与模板链接，不保留两份正文。
