### 预测性返回的设备探测（模拟器已切到手势导航）

模拟器原本是 3 键导航，而预测性返回是**手势导航**才有的行为，因此先前"没效果"。
改用 `cmd overlay enable ...navbar.gestural` + `settings put secure navigation_mode 0` 切换后实测：

| 手势 | 手指按住时面板 | 松手后 |
|---|---|---|
| 极小位移（≤60px） | 不动（257） | 弹回（257） |
| 位移 120px | 跟随（441） | 关闭 |
| 位移 260px | 跟随（705） | 关闭 |
| 位移 700px | 跟随（1578） | 关闭 |

即：面板跟随系统手势进度、松手后或提交或弹回；普通返回（keyevent 4）仍能关闭面板。

面板退场的重复动画也已实测：修复前菜单关闭后 Dialog 窗口在 572ms 后消失（Compose 退场
`panelDepart` 只要 200ms），移除路由宿主的窗口动画后降到 344ms 左右；
页面自己打开的选择器（不经过路由宿主）仍保留窗口动画，实测 315ms 关闭。

### 掉帧的定位（结论是"测得出来，但不是应用在重组"）

按住面板下滑时，给 `BrowserSheetWindow`/`sheetMotion`/`BrowserSheetHost`/`BrowserScreen` 加临时探针，
整个下滑过程中**重组次数都是 0**；`dumpsys gfxinfo` 显示 79 帧里 `Number Slow issue draw commands` 66 帧，
而 `Number Slow UI thread` 只有 7 帧；把背后的网页换成空首页后数字不变（65/80）。
这台模拟器是 SwiftShader 软件渲染（`dumpsys SurfaceFlinger` 可证），系统 UI 自己也有 70% 以上卡顿帧。
**因此模拟器测不出真实掉帧，必须用真机的 `dumpsys gfxinfo com.mybrowser framestats`。**
本版修掉的那处冗余（关闭时多播一次窗口动画）是确实存在的浪费，但它不是"是否掉帧"的证据。

### 未覆盖（必须说明）

- **提交阈值偏小**：模拟器上约 120px 位移即判定为提交（面板高约 2147px，≈5.6%），
  而手指拖动关闭的阈值是 33%。这是系统判定提交、应用只是跟随该判定，不是应用的阈值；
  但仍需在真机上确认"小幅回滑容易被误关"的观感是否可以接受。
- **合成手势不等同真实触摸管线**：上表的数值来自 `input swipe`，真实手指的进度曲线可能不同；
  `uiautomator` 在长按期间不稳定，未能取得每一帧的连续序列。
- **真机帧率仍未测**：本版没有真机帧时间数据，掉帧的最终结论只能由真机给出（见上一节）。
- **元素选择器的真机覆盖有限**：模拟器回归覆盖了 id、唯一 class 与路径三种选择器，
  但真实页面上「选择器匹配数」与「实际消失元素数」的一致性仍建议在真机抽查；
  相对路径图片的临时隐藏也只在模拟器 fixture 上验证过。
- 投屏面板本身没有设备阶段（模拟器无 DLNA 接收器），跳转、位置接管与音量恢复只能靠单元测试
  加真机确认；实体接收器兼容性、DRM / 需鉴权媒体仍未验证。
- 用户脚本的**存储写拒绝应答**只做了单元/协议层核对（Node 覆盖 JS 侧），
  Kotlin 侧监听器的应答路径没有自动化测试。
- **页面文件下载的真机覆盖有限**：模拟器覆盖了 6 MiB（跨 6 个分片）、同一文档连续两次、
  短文件失败与取消清理，但**大文件（数百 MiB）下的内存与磁盘行为、页面中途导航离开、
  以及"页面报的大小与实际发送不一致"**没有设备用例，只有单元层对越界字节的丢弃断言。
  真机上还需确认极端大小下的写入速度与剩余空间不足时的清理提示。
- 无痕 GM 值的跨会话清理由单元测试（`UserScriptStoreTest`）与 `features-scripts` 阶段覆盖；
  "关掉最后一个浏览器窗口但进程仍在，再重新进入无痕"这条 `onCleared` 路径没有直接的模拟器用例。
- 完整 46 阶段矩阵只跑了改动相关的上述阶段；`media-lifecycle` 与 `productivity` 阶段一如既往失败
  （前者在 2026-09-23 的 0.13.0 全量矩阵上就已失败，早于本次改动）。
